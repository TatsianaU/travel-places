# Домашнее задание

## 1. Избранное на Zustand

На занятии мы перевели в store тему — самое маленькое состояние приложения.
Теперь то же самое с избранным: в нём четыре операции, восемь компонентов-
потребителей и persistence, то есть настоящая миграция, а не разминка.

Context-версия из Session 14 должна остаться в проекте рабочей — сделайте
переключение реализаций одной строкой, как это сделано у темы.

Требования:

- `src/features/favorites/favoritesStore.ts` — store с `favoriteIds` и
  действиями `addFavorite`, `removeFavorite`, `toggleFavorite`,
  `clearFavorites`;
- `persist` вместо ручных lazy init и `useEffect` (ключ — свой, не
  `favoriteIds`, чтобы не портить данные Context-версии);
- `devtools` с осмысленными именами действий;
- `useFavorites.ts` становится переключателем между store- и
  Context-версией, как `useTheme.ts`;
- ни один компонент-потребитель не изменился;
- `FavoritesProvider` в `main.tsx` закомментирован (store его не требует);
- проверьте оба варианта переключателем: поведение UI идентично.

Подсказки:

- логика переходов уже написана в `favoritesReducer` — её можно перенести
  в действия store почти дословно;
- `isFavorite` удобнее не хранить в store, а считать в компоненте
  селектором: `useFavoritesStore((s) => s.favoriteIds.includes(id))` —
  тогда карточка перерисуется только при изменении СВОЕГО признака;
- счётчик в шапке подпишите на `favoriteIds.length`, а не на весь массив;
- не забудьте, что `persist` хранит данные в своём формате.

### Проверка выигрыша (необязательно)

Повесьте `useRenderCount` на `Header` и пару карточек и сравните числа
в обеих реализациях при клике по сердечку. Запишите результат в комментарий.

## 2. Панель сравнения мест

Новая функциональность на отдельном store: пользователь отмечает места
«к сравнению», внизу появляется панель с выбранными и кнопкой очистки.

Требования:

- отдельный store (не смешивать с избранным);
- хранить только `id`, данные брать из TanStack Query;
- максимум 3 места, при попытке добавить четвёртое — ничего не происходит;
- кнопка добавления в `PlaceCard` показывает текущее состояние места;
- панель не отображается, когда список пуст;
- выбор сохраняется между перезагрузками;
- панель показывает количество и умеет очищать список.

Подсказки:

- «влезет ли ещё одно место» — это derived value, считайте селектором,
  а не отдельным полем store;
- кнопка очистки не должна подписываться на данные — только на действие;
- если из store нужно несколько значений сразу, вспомните про `useShallow`.

### Ограничение по количеству (необязательно)

Покажите пользователю, почему четвёртое место не добавляется: заблокируйте
кнопки у невыбранных мест, когда лимит исчерпан.

## 3. Сброс формы через key (сложное задание, необязательно)

На занятии мы видели: `PlaceForm` синхронизируется с текущим местом
императивно — `useEffect` + `reset()` + директива `'use no memo'`.
Сделайте декларативный вариант и сравните.

Требования:

- в `EditPlacePage` передайте форме `key` с идентификатором места;
- уберите из `PlaceForm` эффект синхронизации с `placeToEdit`;
- проверьте оба сценария: переход между `/places/:id/edit` разных мест и
  переход «создание → редактирование»;
- убедитесь, что кнопка «Очистить» и ошибки отправки по-прежнему работают;
- в комментарии к `key` напишите одним абзацем, что изменилось и какой
  вариант вы бы оставили в реальном проекте.

Подсказки:

- `key` заставляет React размонтировать старую форму и смонтировать новую —
  вместе с состоянием RHF и локальным `submitError`;
- проверьте, нужна ли после этого директива `'use no memo'`;
- если форма перестала показывать данные при первом заходе — посмотрите,
  в какой момент `placeToEdit` перестаёт быть `undefined`.

Придумайте и опишите случай, в котором сброс через `key` был бы ошибкой:
состояние, которое пользователь ожидает увидеть сохранённым при переключении.
