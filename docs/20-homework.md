# Домашнее задание

## 1. Граница вокруг виджета, а не всей страницы

Сейчас в приложении две границы: вокруг области маршрутов и вокруг
учебной кнопки «Сломать». Между ними — целый этаж, на котором ошибка в
одной карточке кладёт весь список.

Поставьте границу вокруг **отдельной карточки места** в `PlaceList`.

Требования:

- ошибка в одной карточке не должна ронять остальные — на её месте
  появляется компактное сообщение, список продолжает работать;
- сообщение помещается в габариты карточки и не ломает сетку;
- в комментарии — почему граница вокруг карточки уместна, а вокруг,
  например, кнопки «в избранное» была бы избыточной;
- проверьте: временно бросьте ошибку для места с конкретным названием.

Подсказки:

- `ErrorFallback` принимает проп `what` — для карточки подойдёт короткое
  «это место»;
- подумайте, нужен ли здесь сброс через `key` и что должно быть ключом;
- посмотрите, как выглядит сетка, если сломались две карточки из пяти.

### Усложнение (необязательно)

Сделайте так, чтобы сломанная карточка логировала в консоль id места.
Подумайте, откуда границе взять этот id, и объясните в комментарии
выбранный способ.

## 2. Ошибки запросов через границу

У TanStack Query есть опция `throwOnError`: с ней ошибка запроса
превращается в ошибку рендера и попадает в ближайшую границу. Это
альтернатива ручной обработке `isError` на каждой странице.

Переведите **одну** страницу на этот подход и сравните.

Требования:

- страница больше не обрабатывает `isError` сама;
- ошибка загрузки показывает запасной экран границы;
- «Попробовать снова» должна действительно повторять запрос, а не просто
  перерисовывать упавший компонент;
- в комментарии — что стало лучше, что хуже и какой подход вы бы выбрали
  для реального проекта.

Подсказки:

- проверять удобно, остановив `npm run server`;
- ищите в документации Query, как связать сброс границы с повтором
  запроса (`QueryErrorResetBoundary`);
- обратите внимание, что при таком подходе теряется возможность показать
  ошибку **внутри** страницы, сохранив остальную вёрстку.

## 3. Предзагрузка ленивого экрана (со звёздочкой)

Ленивая загрузка экономит трафик, но добавляет паузу в момент перехода.
Приём, который убирает паузу: начать грузить чанк заранее — например,
когда пользователь навёл курсор на ссылку меню.

Требования:

- при наведении на пункт меню «Большая лента» её чанк начинает грузиться;
- повторное наведение не запускает загрузку заново;
- переход после предзагрузки происходит без появления `PageSkeleton`;
- в комментарии — на каких пунктах меню предзагрузка оправдана, а на
  каких навредит (подумайте про мобильные устройства, где наведения нет).

Подсказки:

- `import()` возвращает промис, и повторный вызов для того же модуля
  отдаёт уже загруженный результат — специально ничего кешировать не
  нужно, но проверьте это в Network;
- функцию предзагрузки удобно положить рядом с объявлением `lazy`, чтобы
  путь к модулю был записан один раз;
- измерьте разницу: Network → Slow 4G, наведение и переход против
  перехода без наведения.
