# Домашнее задание

## 1. `toastStore`: правила уведомлений без React

**Цель:** применить приёмы занятия — `toBe`, шпиона `vi.fn()`, изоляцию —
к настоящему коду продукта, а не к учебному примеру.

**Сценарий.** `src/features/toasts/toastStore.js` (Session 17–18) решает,
какие уведомления существуют: `showToast`, `dismissToast`, `clearToasts`
и лимит `MAX_VISIBLE_TOASTS`. На занятии мы пользовались им как
инструментом, а собственные правила store тестами не описаны.

**Требования:**

- файл `toastStore.test.js` рядом со store; ни рендера, ни React —
  только функции и `toastStore.getState()`;
- новое уведомление попадает в список, тон по умолчанию — `success`;
- одновременно уведомлений не больше трёх, и вытесняется САМОЕ СТАРОЕ;
- `dismissToast(id)` убирает только указанное уведомление;
- `dismissToast` с несуществующим id не меняет состояние: та же ссылка
  (`toBe`) и ни одного вызова подписчика (`vi.fn()` +
  `toastStore.subscribe`);
- store живёт в модуле и переживает тесты — очищайте его в `beforeEach`
  через `clearToasts()`. На конкретные значения id не завязывайтесь:
  счётчик id тоже живёт в модуле, и `clearToasts()` его не сбрасывает.

**Критерии готовности:** удаление раннего выхода в `dismissToast` делает
красными только тесты про несуществующий id; замена
`slice(-MAX_VISIBLE_TOASTS)` на `slice(0, MAX_VISIBLE_TOASTS)` — только
тест про лимит; по списку имён тестов можно пересказать правила
уведомлений, не открывая store.

### Усложнение (необязательно)

Проверьте, что в «свежем» модуле первое уведомление получает id `1`.
Понадобится приём из `slowApi.contract.test.js`: `vi.resetModules()` и
динамический `import`.

## 2. `useDelayedFlag` и таймеры

**Цель:** научиться тестировать хук и управлять временем.

**Сценарий.** `src/hooks/useDelayedFlag.js` задерживает показ скелетона на
250 мс, чтобы он не мигал на быстрых ответах. Проверить это руками нельзя
— нужно останавливать время.

**Требования:**

- использовать `renderHook` из Testing Library. Аргументы хука
  передавайте через `initialProps`, а «флаг выключился» — это
  `rerender` с новыми props;
- включить фейковые таймеры (`vi.useFakeTimers`) и обязательно вернуть
  настоящие в `afterEach`;
- проверить три вещи: сразу после включения флага хук возвращает
  `false`; после истечения задержки — `true`; если флаг выключился раньше
  срока, `true` не наступает никогда;
- продвигать время внутри `act`: колбэк таймера меняет состояние хука в
  обход React.

**Подсказка на будущее.** Если в тесте понадобится `user-event` вместе с
фейковыми таймерами (а в Session 23 понадобится), ему нужно объяснить,
как двигать время:

```ts
const user = userEvent.setup({ advanceTimers: vi.advanceTimersByTime })
```

Без этого клик зависнет: `user-event` ждёт настоящих таймеров, которых
больше нет.

**Критерии готовности:** тесты выполняются мгновенно (никаких реальных
250 мс); если хук начнёт ждать дольше переданной задержки (например,
`delay + 1`), краснеет тест про истечение задержки; если удалить очистку
таймера в эффекте, краснеет тест про ранее выключение флага.

## 3. Тесты для `ErrorBoundary`

**Цель:** проверить компонент, который существует ради ошибок.

**Сценарий.** `src/components/ErrorBoundary/ErrorBoundary.jsx` ловит
ошибки рендера, а в Session 21 у него появился сброс по `resetKey`. Тест
должен зафиксировать оба поведения.

**Требования:**

- вспомогательный компонент, который бросает ошибку при рендере
  (по props — чтобы можно было «починить» его между рендерами через
  `rerender`);
- запасной экран — настоящий `ErrorFallback`. Рендерить через
  `renderWithProviders`: в `ErrorFallback` есть ссылка «На главную», а
  ссылке нужен роутер;
- проверить, что вместо упавшего поддерева показан запасной экран;
- проверить, что смена `resetKey` возвращает нормальный экран, а
  повторный рендер с прежним `resetKey` — нет;
- проверить, что кнопка «Попробовать снова» из `ErrorFallback` работает.

**Важно:** React печатает пойманные ошибки в консоль, и вывод теста
станет красным от чужих сообщений. Приглушите их на время теста:

```ts
vi.spyOn(console, 'error').mockImplementation(() => {})
```

Конструкция `restoreMocks: true` в конфиге вернёт настоящий `console.error` перед следующим тестом
автоматически.

**Критерии готовности:** если удалить `componentDidUpdate` из
`ErrorBoundary`, красным становится ровно тест про `resetKey`, остальные
остаются зелёными.

### Усложнение (необязательно)

Добавьте тест на то, чего граница НЕ ловит: ошибку в обработчике
`onClick`. Он должен показать, что запасной экран не появляется, — и тем
самым задокументировать ограничение, о котором легко забыть.

**Подсказка.** Ошибка из обработчика никуда не исчезает: React передаёт
её в глобальное событие `error` у `window` — туда же, куда в браузере
смотрят системы мониторинга. Vitest считает такую ошибку необработанной
и роняет весь прогон («Unhandled Errors»), даже если сам тест зелёный.
Подпишитесь в тесте на `error` у `window`, вызовите в подписчике
`event.preventDefault()`, проверьте, что подписчик вызван, а запасного
экрана нет, — и не забудьте отписаться.

## 4. Схемы Zod (со звёздочкой)

**Цель:** увидеть, что правила валидации — тоже чистая логика, и
проверить их на самом дешёвом этаже.

**Сценарий.** `placeFormSchema` и `registrationSchema` описывают правила
форм. Проверяем не Zod — он протестирован без нас, — а НАШИ правила,
записанные на Zod: минимальные длины, требования к паролю, совпадение
паролей, «год обязателен для посещённых мест». Форму целиком в Session 23
будем проверять иначе: только то, что она связана со схемой. Каждое
правило по отдельности проверяется здесь, без React.

**Требования:**

- для каждой схемы: один тест на корректные данные и по тесту на каждое
  наше правило (короткое название, год вне диапазона, пароль без цифры,
  несовпадение паролей, посещённое место без года);
- проверять не только факт ошибки, но и то, к какому ПОЛЮ она относится.
  Пригодятся `schema.safeParse(data)` — он не бросает исключение, а
  возвращает результат — и `z.flattenError(result.error).fieldErrors`;
- сообщения сравнивать по вхождению, а не целиком — иначе правка текста
  сломает тест;
- отдельным тестом проверить обещание из комментария к полю `email` в
  `registrationSchema`: адрес с пробелами по краям и заглавными буквами
  после разбора становится аккуратным (`'  Ivan@Mail.EXAMPLE  '` →
  `'ivan@mail.example'`).

**Если тест про email покраснел — это не ошибка теста.** Выясните, в
каком порядке Zod выполняет проверку формата и обрезку пробелов, решите,
что исправить — схему или комментарий, — и объясните, почему в браузере
пользователь этой ошибки не видит (подсказка: как `input type="email"`
обращается с пробелами). Хороший пример того, как модульный тест видит
то, чего не видит интеграционный.

**Критерии готовности:** по списку тестов можно прочитать правила
валидации, ни разу не открыв саму схему. Это и есть «тест как
документация».
